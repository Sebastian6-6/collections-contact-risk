- 2026-11-09 Gold column naming (user decision, prefixes corrected by the user): Portuguese, lowercase snake_case, type prefix + subject: cod_ code, nome_ name, desc_ description, num_ number (not necessarily numeric: num_cpf, num_telefone), dt_ date, hr_ time, qt_ quantity, vl_ value, tx_ rate, tp_ type, sit_ status, sigla_ acronym, flag_ boolean, sk_ surrogate key. Inspired by the DataSUS naming norm but with longer prefixes; this is the project's own convention. Unioned dims carry a lineage column with the contributing provider(s) (e.g. desc_provedores_origem = 'alfa|gama'); per-attribute origin where a conflict was resolved (detail in Stage 6).
- 2026-11-09 Gold column order (user decision): dims = sk_ PK -> natural key (num_cpf) -> attributes, where each code is immediately followed by its own description (cod_x, desc_x, cod_y, desc_y, cod_z...; a code without description stands alone) -> names -> numbers/values -> flags -> dates -> lineage last. Facts = sk_ PK (if any) -> sk_ FKs to dims -> source identifiers -> measures -> flags -> dates -> lineage last.
- 2026-11-09 Missing references stay NULL (user decision; project's own convention, document it WITHOUT citing Kimball or any external methodology): no placeholder "unknown" row is created in any dimension, because the case rule "Modelos não geram linhas que não existam na origem" forbids rows absent from the source; a fact whose dimension reference cannot be resolved keeps the FK as NULL ("ausência de dado é NULL", same rule set). Consequence to document: joins from facts to dims use LEFT JOIN where the FK is nullable, and dbt relationship tests ignore NULL by design. Must be written in docs/decisoes-de-modelagem.md (Stage 6/10).
- 2026-11-09 Skill evals run at the start of development (topic fundacao-do-repositorio), not during design (user decision).
- 2026-11-09 Execution model (user decision): one topic per execution front with a detailed PLAN.md (STATE.md stays short), a master PLAN.md in this topic, orchestrated agents committing their own logical changes (storytelling, few commits; fix/refactor commits carry the measured gain), a final plan-review step, then execution topic by topic with a single approval after the review. A storytelling document is kept outside the repository.
